# מתג ההפעלה והכיבוי של התשלומים הדיגיטליים ב-D1 ונוהל חירום (מומש בענף PR #155, 14.10.2026)

סטטוס: קוד ובדיקות בענף; **לא הופעל בשום מסד**; לא נכתבה שורת מתג באף סביבה; שני הדגלים ב-`wrangler.toml` נשארו `false`; אין מיגרציה (משתמש בטבלת `settings` הקיימת); אין שינוי production.

## 1. מה זה
שורה אחת בטבלת `settings` (מפתח `digital_checkout_switch`, ערך JSON) שנבדקת בכל בקשת תשלום ציבורית. היא שכבה **נוספת מעל** הדגלים ובדיקות התצורה ואינה עוקפת אותם: קודם הדגלים והתצורה (בלי קריאת מסד כשהם כבויים), ואחר כך המתג.

## 2. המצבים (לפי החלטתך)
| מצב | הצעת מחיר | הזמנה חדשה | חיוב (capture) |
|---|---|---|---|
| **אין שורה / שורה לא תקינה / המסד לא נקרא** | חסום | חסום | **חסום** (כשל סגור) |
| **open** (חובה `closesAt`) | פתוח | פתוח (בכפוף לתקרות) | פתוח |
| **closed** — סגירה הדרגתית | חסום | חסום (גם ניסיון חוזר) | **מותר רק להזמנה שנוצרה לפני רגע הסגירה, ועד 30 דקות אחריו** |
| **frozen** — חירום | חסום | חסום | **חסום** |

**בכל מצב** ממשיכים לפעול: עיבוד webhooks, מסירת רכישות ששולמו כבר (כולל השלמה מקומית של הזמנה שכבר נתפסה והחזרת תוצאה שמורה), הורדות, הנפקה מחדש, החזרים ומחלוקות, מיילים והתראות.

- `open` חייב `closesAt` (עתיד, עד 90 יום); **נאכף בכל בקשה בלי תלות ב-cron**: מרגע `closesAt` המתג נחשב `closed` וחלון 30 הדקות נמדד מ-`closesAt`.
- `maxOrders` (אופציונלי): תקרת הזמנות דיגיטליות שנוצרו מאז הפתיחה (`openedAt`), נאכפת **אטומית** — ה-`INSERT` עצמו כולל את הספירה. ניסיון חוזר עם אותו `Idempotency-Key` מחזיר את ההזמנה הקיימת ואינו נספר שוב; כל הזמנה שנוצרה נספרת (גם נטושה). אם בקשות מקבילות מגיעות לתקרה אחרי שנוצרה הזמנת PayPal, הזמנת PayPal נשארת יתומה ובלתי נראית ללקוח (לא נשלח לו קישור) והוא מקבל הודעת "זמנית לא זמין".
- `photoIds` (אופציונלי): רשימת תמונות מותרת, נאכפת בשרת בהצעת המחיר ובהזמנה (לא מהדפדפן). הזמנה שכבר קיימת אינה מושפעת.
- הלקוח מקבל תמיד את אותה הודעת 503 "הרכישה זמנית לא זמינה", בלי הסיבה.

## 3. שינוי המתג
**דרך אדמין** (`POST /api/admin/paypal/switch`, אימות אדמין, `Idempotency-Key` ו-`reason` חובה; `GET` מציג את המצב):
```
{ "state": "open",   "reason": "canary of 3", "closesAt": "2026-10-20T12:00:00Z", "maxOrders": 3, "photoIds": ["photo-1"] }
{ "state": "closed", "reason": "end of canary" }
{ "state": "frozen", "reason": "price bug" }
```
- כל שינוי נרשם בטבלת הביקורת (`SWITCH`: מפתח, מצב חדש, "מ-ל", תקציר, שחקן `admin`; ללא קישורים, כתובות או סודות). אותו מפתח = חזרה, בלי כתיבה נוספת.
- `closed` ו-`frozen` עובדים גם כשתצורת PayPal שבורה או שהשורה המאוחסנת פגומה. `open` דורש תצורת PayPal תקינה.
- מ-`frozen` אי אפשר ישר ל-`open`: קודם `closed`. מעבר מ-`frozen` ל-`closed` **שומר את זמן העצירה המקורי**, כך שאינו פותח חלון חדש של 30 דקות. פתיחה חדשה מתחילה תקופת תקרה חדשה.
- כלי העזר `window-tools.ps1` אינו כולל עדיין פקודת switch (ניתן להוסיף).

## 4. נוהל חירום ב-D1 (בלי להיכנס לאתר; בלי פריסה)
הפקודות מבוצעות מול ה-D1 של הסביבה (production: `amit-photos-db`). מומלץ לשמור את הנוהל זמין גם מחוץ לקוד.

1. **עצירה מלאה מיידית (הכי פשוט): מחיקת השורה.** חוסם הזמנות חדשות **וגם חיובים**:
   `npx wrangler d1 execute amit-photos-db --remote --yes --command "DELETE FROM settings WHERE key = 'digital_checkout_switch'"`
2. **הקפאה מסומנת (frozen):**
   `npx wrangler d1 execute amit-photos-db --remote --yes --command "INSERT INTO settings (key, value) VALUES ('digital_checkout_switch', '{\"state\":\"frozen\",\"closedAt\":\"<ISO-עכשיו>\",\"updatedBy\":\"d1\"}') ON CONFLICT(key) DO UPDATE SET value = excluded.value"`
3. **סגירה הדרגתית (closed):** כנ"ל עם `"state":"closed"` ו-`closedAt` של עכשיו.
4. **אימות** (אחרי כל צעד): `POST /api/paypal/create-order` מחזיר 503, ו-`GET /api/payments-status` מחזיר `digitalEnabled:false`. לתעד ב-HANDOFF.
5. פתיחה מחדש רק דרך נתיב האדמין (`closed` ואז `open`), באישורך.

פריסה (גם של סוכן), `wrangler rollback` או revert **אינם משנים** את השורה: שום קוד, קובץ הגדרות, מיגרציה, סקריפט bootstrap או workflow אינו כותב אותה (נבדק במבחן סטטי). לכן הגדרה שנעשתה בחירום נשארת עד שמישהו משנה אותה במכוון.

## 5. אימות (בדיקות)
`tests/paypal-checkout-switch.test.mjs` (15 בדיקות, SQLite אמיתי בסכימת production, PayPal מדומה): פענוח קפדני של השורה; `closesAt` (לפני, בדיוק, אחרי); כשל סגור (חסר, JSON שבור, מצב לא ידוע, פתיחה ללא זמנים, שגיאת מסד) עם אפס קריאות ל-PayPal; פתוח לא עוקף דגלים ותצורה; סגירה הדרגתית בגבולות 29:30 ו-31 דקות והזמנה שנוצרה אחרי הסגירה; `frozen` — חסום ואילו מסירה, הורדה, הנפקה מחדש, webhook השלמה והחזר ממשיכים; מעברי מצבים, אי-דריסה בבקשה לא תקינה, חזרה על מפתח; תקרת הזמנות עם 8 בקשות מקבילות (בדיוק 2 נוצרות), חזרה עם אותו מפתח, חמש בקשות עם מפתח אחד, תקופת תקרה חדשה; רשימת תמונות כולל זיופים; הצהרות סטטיות על "הפריסה לא נוגעת במתג"; ונוהל ה-D1. הכשלת הבדיקות נבדקה בהשחתות (אכיפת `closesAt`, חלון 6 שעות, פתיחה בכשל קריאה, `frozen` מתיר חיוב, תקרה לא אטומית, הסרת שער החיוב) — כולן נתפסות. בדיקות קודמות עודכנו להכין שורת `open` במסד הבדיקה.

## 6. פערים והחלטות
1. **לא נבדק על D1 אמיתי** (רק SQLite): תחביר ה-`ON CONFLICT` ו-`INSERT … SELECT` עם ספירה, `meta.changes`, ובקשות מקבילות אמיתיות. נדרש אישורך לשיטה: מסד זמני חדש ומבודד (מומלץ; נוצר ונמחק) או שורות סינתטיות במסד ה-Sandbox הקיים.
2. **הודעת "סגור" ללקוח** היא כללית. אין עדיין עמוד/הודעה ייעודית ל"קאנרי הסתיים".
3. **כל הזמנה נספרת** לתקרה, גם נטושה: קאנרי של N עלול להיגמר מוקדם. אפשר לספור רק הזמנות לא נטושות (דורש החלטה).
4. **90 ימים** כתקרת פתיחה ו-**30 דקות** כחלון הסגירה — לפי החלטתך; ניתן לשנות.
5. **הדגלים ב-`wrangler.toml`** נשארים `false`. שינוי עתידי דורש אישור נפרד; עם המתג, "פתיחה" היא פעולת מתג, והדגלים צריכים להיות `true` כדי שהמתג יהיה אפקטיבי (יש להחליט מתי ובאיזה PR).
6. נוהל התגובה (`docs/payment-incident-response-runbook-2026-10-14.md`) מעודכן להפנות לנוהל זה.
