### The language bug and its fix

Symptom: English phone purchase returned to a Hebrew page. Cause: the page read its language only from `?lang=` or `localStorage.lang`, while the PayPal return/cancel URLs (`/checkout/?approved=1`, `/checkout/?cancelled=1`) carried no `lang`, and opening the page with `?lang=en` stored nothing. Fix `836ab625`: the client saves the language with the pending attempt, sends it to `create-order` and resolves it with `resolveCheckoutLang` (explicit `?lang` > pending attempt > site preference > Hebrew), the success URL keeps `?lang=en`; the server appends `&lang=en` to the PayPal return and cancel URLs for English attempts only; `checkout/index.html` cache-bust updated (`?v=a8d112a3`). Tests: 3 unit tests (16/16 in the file) and 3 mocked-browser scenarios; all 9 GitHub checks green (including `digital-checkout-browser`). **The fix is NOT yet verified live**: it was deployed after the window, so a real English round trip must be repeated.

## 35. recover-fulfillment implemented (14.10.2026, night)

- **Route:** `POST /api/admin/paypal/recover-fulfillment` (admin login required by the router; body `paypalOrderId` + `reason` only; `Idempotency-Key` header). Any other field (a capture id, a token, an amount) is refused with 400 before anything is read or called.
- **Steps:** eligibility from our database (digital, exactly `FULFILLING`, capture id and token recorded, no refund/reversal/revocation, no review state, no dispute) → the slot is taken in ONE statement (no other recovery of that order started in the last 10 minutes; order still FULFILLING with no after-sale state) → PayPal is asked read-only (`GET /v2/checkout/orders/<id>`) and must confirm order id, order `COMPLETED`, `custom_id`, OUR recorded capture id with status `COMPLETED` (so PENDING/DECLINED/REFUNDED/PARTIALLY_REFUNDED all refuse), currency and amount → the order row is re-read (a refund, dispute or webhook that landed meanwhile stops it, or reports it already completed) → the shared `finalizeDigitalPayPalOrder` (the same function as the webhook and the buyer's retry): the one stored token (`INSERT OR IGNORE`), refund re-checks before and after minting, status flip guarded by `WHERE status='FULFILLING'`, mail only from the call that flipped it. The response is only `{ok, replayed, status}`: no link, no capture id, no payer address, no PayPal text.
- **Never:** no capture endpoint and no POST to PayPal (source test + the fake counts every request), no order creation, no capture id from the request, no manual D1 edit. Works while the switch is `frozen`/`closed` and the payment flags are `false`.
- **Audit** (`paypal_order_actions`, action `RECOVER_FULFILLMENT`, no schema change): one row per key with `STARTED` / `DONE` / `FAILED` / `REFUSED` and an `outcome=` code; the admin's reason is cut to 150 characters and scrubbed of links, UUID-like and long token-like values. A used key is not reusable after a failure/refusal (409 `KEY_ALREADY_USED_USE_A_NEW_KEY`); a failed attempt does not lock the order.
- **Interruption:** an exception mid-way returns a bare 500 `RECOVERY_INTERRUPTED`, leaves the row `STARTED` and the SAME key resumes (one token, one mail); a different key is held off for 10 minutes.

## 36. Dispute gap in the shared completion path closed (14.10.2026, night)

- **Problem:** `finalizeDigitalPayPalOrder` (used by the webhook, the buyer's capture retry and `recover-fulfillment`) only blocked terminal refund states, and only through reads before the writes; a dispute or review recorded in between could still be delivered.
- **Fix (`paypal-orders.js`):** the block now covers every after-sale state and `dispute_open`, and is enforced inside the writes: the token INSERT is `INSERT … SELECT … WHERE EXISTS(order with after_sale_state='NONE' AND dispute_open=0)` and the completion UPDATE carries the same condition; if either refuses, the response is 409 `ORDER_UNDER_REVIEW` (or `ORDER_REFUNDED`), the order stays `FULFILLING` and an already minted link is withdrawn (`REVIEW_BEFORE_DELIVERY`). The dispute/review event handler now withdraws unused links of an order that is not `COMPLETED` (single statement), so an event arriving after the token was minted cancels it; after a person's `release` the SAME stored link is restored and the order completes once; a `revoke` is final. Before migration 0003 (no review columns) the old behaviour is unchanged. A recovery retry that is now refused releases its 10-minute slot (REFUSED).
- **Not claimed:** a dispute PayPal has not yet reported is unknown to the system, so a link delivered before the event is recorded cannot be stopped; a delivered link is not cancelled automatically on a dispute (policy: a person decides). Documented in section 6 of `docs/stuck-fulfilling-recovery-design-2026-10-14.md` and in the runbook rule 3.
