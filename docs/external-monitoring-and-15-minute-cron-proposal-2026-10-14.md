# הצעה: ניטור חיצוני וסבב בדיקה של 15 דקות (לעיונך; לא הופעל, לא שונה)

סטטוס: **הצעה בלבד.** לא שונה `wrangler.toml`, לא נוסף cron, לא נוסף workflow, לא הופעלו התראות ב-production. הדגלים `false`.

## 1. מה חסר היום
1. תקלות שמתגלות רק בסבב (מסירה תקועה, כשל מייל סופי, שולם בלי קישור, מסד מאחור) מתגלות עד **שעתיים** אחרי, כי ה-cron של production הוא `0 */2 * * *`.
2. **Worker שנפל או מחזיר 5xx** אינו יכול להתריע על עצמו. PayPal רק מציג כשלי מסירה בלוח. `health-check.yml` בודק רק את דף הבית **פעם ביום**.
3. אין בדיקה שתשלומים אכן **סגורים** כשצריך (או פתוחים כשצריך).

## 2. ממצא חשוב שמשפיע על סבב ה-15 דקות
הפונקציה `scheduled` ב-`worker.js` מריצה היום **את כל ארבע המשימות בכל הפעלה של כל cron**: סנכרון Pinterest (יוצר פינים), יצירת טיוטת ניוזלטר (קריאות ל-Anthropic, עולות כסף), רצף Welcome (מיילים), וסבב המייל/בריאות של התשלומים. הפונקציה אינה בודקת איזה cron הפעיל אותה (`event.cron`).

לכן **הוספה פשוטה של `*/15 * * * *` ל-`wrangler.toml` תריץ את Pinterest והניוזלטר כל 15 דקות**, וזה אסור. החלופה הבטוחה:

```js
async scheduled(event, env, ctx) {
  const frequent = event.cron === '*/15 * * * *';
  if (frequent) {                       // רק ההתראות והסבבים הקלים
    ctx.waitUntil(runPaymentHealthCheck(env).catch(() => {}));
    ctx.waitUntil(retryDownloadLinkEmails(env).catch(() => {}));
    return;
  }
  ctx.waitUntil(runPinterestCronSync(env));     // כמו היום, רק בשני ה-cron הקיימים
  ctx.waitUntil(runNewsletterCron(env));
  ctx.waitUntil(runWelcomeSequenceCron(env));
  ctx.waitUntil(retryDownloadLinkEmails(env).catch(() => {}));
  ctx.waitUntil(runPaymentHealthCheck(env).catch(() => {}));
}
```
ביטויי ה-cron הקיימים (`0 */2 * * *`, `0 9 1,15 * *`) יישארו זהים והמשימות הקיימות ירוצו בהם בדיוק כמו היום; רק הטריגר החדש מפעיל את המשימות הקלות. שינוי הקוד קטן, בר בדיקה (בדיקת יחידה על `event.cron`), ולא נעשה.

**עלות ורעש:** כל סבב תשלומים הוא כ-7 שאילתות קריאה ב-D1 ו-0 שיחות חיצוניות כשהכול תקין (התראות נשלחות רק על תקלה חדשה, פעם אחת). 96 הפעלות ביום.

## 3. אפשרויות לניטור חיצוני

| אפשרות | מה בודקת | עלות/סיכון | יתרונות | חסרונות |
|---|---|---|---|---|
| **א. GitHub Actions כל 15 דקות** (workflow חדש) | `GET /` ו-`GET /api/payments-status` ו-`GET /api/paypal/quote` (קריאה ציבורית); כשל = ה-workflow נכשל ומייל מ-GitHub | חינם; צורך דקות Actions (כ-5 שניות להפעלה) | כבר בשימוש במאגר; ללא ספק חדש | מתוזמן "במאמץ מיטבי" (עיכובים של דקות), ה-workflow ישן יושבת אחרי 60 יום ללא פעילות במאגר |
| **ב. שירות uptime חיצוני** (למשל UptimeRobot או Better Stack, שכבה חינמית) | אותן כתובות, ממיקומים שונים, התראה במייל/טלגרם | חשבון צד שלישי; כתובות ציבוריות בלבד | עצמאי מ-Cloudflare ומ-GitHub, מרווח של דקות | ספק נוסף; אין גישה לנתיבי אדמין |
| **ג. התראות Cloudflare** (Notifications) על שיעור שגיאות Worker / כשל Builds | שגיאות 5xx ופריסות שנכשלו | חינם בחשבון קיים | רואה את מה שהשרת רואה | תלוי בתכונות החשבון; לא מכסה "חשבון Cloudflare כולו נפל" |
| **ד. נתיב ציבורי בוליאני `GET /api/payments-health`** | מחזיר רק `{ok:true/false}` על פי תמונת המצב (ללא מזהים) | חשיפה: ציבורי יוכל לראות שיש תקלה | מאפשר לבדיקות א/ב לראות בעיות עומק בלי סיסמת אדמין | דורש החלטה (חשיפה מינימלית) ומימוש; לא קיים היום |

**המלצה:** א + ג, ובהמשך ד: workflow של GitHub כל 15 דקות לבדיקות ציבוריות, התראות Cloudflare על שגיאות, ו-`payments-health` בוליאני רק אם תאשר את החשיפה. בדיקה חיצונית שנייה (ב) מומלצת אם התשלומים נפתחים לקהל. **אל תשמור את סיסמת האדמין ב-GitHub Secrets** לצורך בדיקות; אין צורך בה בבדיקות הציבוריות.

## 4. מה ייבדק ומה ההתראה
- דף הבית: סטטוס 200 בתוך 15 שניות.
- `/api/payments-status`: JSON תקין; מצב הדגלים תואם **למצב המצופה** (בזמן שהתשלומים אמורים להיות סגורים: `enabled:false`; חריגה = התראה "פתוח שלא מתוכנן").
- `/api/paypal/quote?photoId=…&sku=large`: 200, מחיר תקין ומטבע `ILS` (מגלה תקלת מחיר).
- כשל אחד בודד לא מתריע; שני כשלים רצופים (30 דקות) כן. התראה מתנקה כשחזרה תקינות.

## 5. החלטות נדרשות ממך
1. לאשר את שינוי `scheduled` (ניתוב לפי `event.cron`) ואת הוספת `*/15 * * * *` ל-`wrangler.toml` (שינוי production, ייפרס עם המיזוג).
2. לבחור אפשרויות ניטור חיצוני (א, ב, ג, ד) ומי מקבל את ההתראות.
3. האם לחשוף `payments-health` בוליאני ציבורי.
4. ספי ההתראה (שני כשלים רצופים; 2 שעות להזמנה תקועה) והאם להקשיח.
5. מועד: לפני הקאנרי, ולא אחרי.

## 6. אימות מוצע (אחרי אישור, בלי production)
1. בדיקת יחידה על `scheduled`: ה-cron התדיר מפעיל רק את המשימות הקלות, ושני ה-cron הקיימים מפעילים בדיוק את הקבוצה הקיימת.
2. ב-Preview אין cron, ולכן בדיקה חיה של הניתוב אינה אפשרית שם; הוכחה בבדיקת יחידה ובהפעלה מבוקרת אחת ב-production לאחר אישור נפרד, עם עיון בלוג הסבב הראשון.
3. הרצת ה-workflow החיצוני במצב `workflow_dispatch` מול production (קריאות ציבוריות בלבד).
